# 비밀번호 저장 설계

## 무엇을 지키고, 무엇을 지키지 않는가

**지킨다: 데이터베이스와 백업.** 값은 서버 키로 AES-256-GCM 암호화해서 저장하므로,
DB 덤프나 백업 파일만 새어나가도 비밀번호는 열리지 않는다.

**지키지 않는다: 서버 자체.** 서버는 키를 가지고 있으므로 값을 복호화할 수 있다.
나스에 루트로 들어갈 수 있는 사람은 `.env`를 읽어 전부 열 수 있다.

이건 의도한 선택이다. 예전에는 브라우저에서 마스터 패스워드로 암호화해 서버도 못 여는
구조였지만, 그러면 같은 프로젝트 멤버끼리 같은 항목을 열게 하려고 키 교환 계층(RSA 키쌍,
프로젝트 키 배포)을 통째로 얹어야 한다. **개인 나스에 두는 개발용 자격증명**에는 그 비용이
맞지 않아서 걷어냈다. 은행·시스템 계정처럼 서버 관리자에게도 감춰야 하는 값은 여기 두지 않는다.

## 흐름

1. 저장할 때 서버가 **AES-256-GCM**으로 암호화해 `Secret.valueCipher`에 넣는다
   (`src/lib/secret-crypto.ts`). 형식은 `iv:암호문:태그`, 각각 base64.
2. 목록(`GET /api/secrets`)은 **값을 절대 싣지 않는다.** 제목·계정·URL·메모만 나간다.
3. "보기"/"복사"를 누를 때만 `GET /api/secrets/[id]/value`로 그 한 건을 복호화해 받는다 -
   보관함을 훑어보는 것만으로 모든 비밀번호가 브라우저(와 중간 프록시 로그)로 흘러가지 않게.
4. 클립보드 복사 시 **30초 후 자동 삭제** (그 사이 다른 값이 복사됐으면 건드리지 않는다).

## 암호화 키

키는 `.env`의 **`AUTH_SECRET`에서 파생**한다(`sha256("scvnote-secret-v1:" + AUTH_SECRET)`).
변수를 따로 두지 않은 건 기존 설치가 `.env`를 손대지 않고 업데이트되게 하기 위해서다.

**따라서 `AUTH_SECRET`을 바꾸면 저장된 비밀번호를 전부 못 읽는다.** 세션만 무효화되는 게
아니다. 바꿔야 한다면 먼저 항목들을 다른 곳에 옮겨 적어두고, 바꾼 뒤 다시 입력해야 한다.

## 누가 무엇을 보는가

노트·할 일과 **완전히 같은 규칙**이다.

- **미분류**(`projectId = null`): 만든 사람만 본다.
- **프로젝트에 넣은 항목**: 그 프로젝트 멤버 전원이 보고, 값도 열고, 수정·삭제도 한다
  (공유 노트와 같은 권한). 별도의 키 전달 절차 같은 건 없다.
- 항목을 프로젝트 안팎으로 옮기는 것도 그냥 된다 - 값을 다시 암호화할 필요가 없으므로.

## 암호화되지 않는 필드

`title` / `username` / `url` / `memo` 는 평문이다. 검색이 가능해야 하기 때문이다.
**정말 민감한 정보는 이 필드에 쓰지 않는다.**

## MCP(Claude 연동) 범위

`list_secrets`는 `select`에서 `valueCipher`를 **명시적으로 제외**한다. 제목·계정·URL·메모만
반환한다. 서버는 이제 값을 복호화할 수 있으므로, MCP로 값이 새지 않는 건 이 `select`가
막고 있기 때문이다 - 값을 MCP로도 읽고 싶다면 그때 도구를 따로 만들어야 한다.

## HTTP로 접속해도 된다

브라우저 암호화를 걷어냈으므로 `crypto.subtle`(보안 컨텍스트 전용)에 의존하지 않는다.
`http://192.168.x.x:3000` 같은 평문 LAN 주소에서도 그대로 동작한다. 다만 그 구간에서는
값이 네트워크를 평문으로 지나가므로, 신뢰할 수 없는 망에서는 HTTPS(리버스 프록시나 VPN)를
앞에 두는 것이 좋다.
